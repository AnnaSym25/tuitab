# MCP-сервер

> 🇬🇧 [This page in English](../en/mcp.md) · [← Оглавление документации](README.md)

`tuitab --mcp` превращает бинарник в сервер [Model Context Protocol](https://modelcontextprotocol.io).
Ассистент, которому дали файл с данными, считает по нему движком tuitab, а не в уме.

Смысл узкий, и его стоит назвать прямо: **языковая модель, которую попросили
сложить колонку, выдаст правдоподобное число.** Отправить вопрос настоящему
движку и прочитать ответ — это разница между отчётом, по которому можно
действовать, и отчётом, который придётся перепроверять.

## Подключение

**Claude Code** — одной командой:

```sh
claude mcp add tuitab -- tuitab --mcp
```

Добавьте `-s user`, чтобы сервер был доступен во всех проектах, а не только в
текущем.

**Claude Desktop** — `~/Library/Application Support/Claude/claude_desktop_config.json`
на macOS, `%APPDATA%\Claude\claude_desktop_config.json` на Windows:

```json
{
  "mcpServers": {
    "tuitab": {
      "command": "/opt/homebrew/bin/tuitab",
      "args": ["--mcp"]
    }
  }
}
```

Полный путь важнее, чем кажется: приложение стартует не из вашей оболочки и может
не видеть `PATH`. Свой путь покажет `which tuitab`.

**Cursor, Windsurf, Zed** — тот же блок в их `mcp.json`.

**Что угодно ещё** — это обычный stdio-сервер. Запускаете подпроцессом, пишете в
stdin JSON-RPC по строке на сообщение, читаете ответы из stdout. Принимаются
версии протокола `2025-06-18`, `2025-03-26` и `2024-11-05`.

## Проверка

Вообще без клиента:

```sh
printf '%s\n' \
 '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"t","version":"0"}}}' \
 '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
 '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' | tuitab --mcp
```

Во втором ответе — четыре инструмента. В Claude Code то же покажет `/mcp`.

## Четыре инструмента

| Инструмент | На что отвечает |
|------------|-----------------|
| `tuitab_inspect` | Что в файле — листы или таблицы, имена колонок, выведенные типы, число строк, несколько строк примера |
| `tuitab_query` | Всё вычислительное, конвейером операций |
| `tuitab_describe` | Статистический профиль каждой колонки |
| `tuitab_jq` | jq-программа по вложенным JSON, JSONL, YAML или TOML |

`tuitab_inspect` идёт первым в любом сценарии. Имена колонок, угаданные по имени
файла, ошибочны достаточно часто, чтобы стоить лишнего обращения.

## Операции

`tuitab_query` принимает `source` и список `ops`, применяемых по порядку — каждая
к результату предыдущей.

```json
{
  "source": {"path": "/data/sales.xlsx", "container": "Q3"},
  "ops": [
    {"filter": [{"col": "status", "op": "eq", "value": "closed"}]},
    {"compute": {"name": "margin", "expr": "revenue - cost"}},
    {"group_by": {"by": ["region"], "agg": [{"col": "margin", "fn": "sum"}]}},
    {"sort": {"by": [{"col": "margin:sum", "desc": true}]}}
  ]
}
```

| Операция | Примечания |
|----------|------------|
| `filter` | Элементы объединяются через AND. Операторы: `eq`, `ne`, `gt`, `ge`, `lt`, `le`, `in`, `not_in`, `contains` (регулярное выражение), `between`, `is_empty`, `not_empty` |
| `select` | Оставить эти колонки в этом порядке |
| `sort` | `{"col": …, "desc": …}` для одного ключа, `{"by": [{…}, {…}]}` для нескольких |
| `compute` | Вычисляемая колонка из выражения |
| `group_by` | Ровно запрошенные агрегаты в запрошенном порядке |
| `aggregate` | Общий итог — одна строка, без группировки |
| `frequency` | Распределение по частоте, с колонками `Count` и `Pct` |
| `pivot` | Строки по `index`, колонки по `on`, ячейки по `formula` |
| `join` | С другим файлом, `how`: inner / left / right / outer |
| `dedup` | По одной строке на ключ. `keep`: first, last, min, max, random |
| `duplicates` | Только строки, чей ключ повторяется |
| `sample` | `n` случайных строк |
| `window` | Колонка, вычисленная из строк вокруг каждой строки. `order_by` задаёт порядок внутри окна, не меняя порядок таблицы |
| `transpose` | Таблица на попа, или одна её строка |
| `limit` | Первые `n` строк |

Для OR альтернативы заворачиваются в `any_of`:

```json
{"filter": [
  {"any_of": [{"col": "region", "op": "eq", "value": "North"},
              {"col": "region", "op": "eq", "value": "South"}]},
  {"col": "amount", "op": "gt", "value": 1000}
]}
```

что читается как `(North OR South) AND amount > 1000`. Один уровень вложенности.

Чтобы сравнить две колонки, поставьте колонку туда, где стоял бы литерал:

```json
{"col": "revenue", "op": "gt", "value": {"col": "cost"}}
```

`HAVING` из SQL — это `filter` после `group_by`.

### Оконные функции

```json
{"window": {"fn": "rank", "col": "salary", "over": ["department"],
            "as": "rank_in_dept", "desc": true}}
```

`row_number`, `rank`, `dense_rank`, `cum_sum`, `lag`, `lead`, агрегаты партиции
`sum` / `avg` / `min` / `max` / `count`, размноженные по её строкам, и
`pct_of_total`.

`over` перезапускает окно на каждой группе; без него окно — вся таблица.

`order_by` задаёт, что значит «до», для `cum_sum`, `lag`, `lead` и `row_number` —
четырёх функций, читающих строки по порядку:

```json
{"window": {"fn": "cum_sum", "col": "amount", "order_by": ["date"],
            "over": ["region"], "as": "running_total"}}
```

Порядок применяется **только к окну**: ответ возвращается к тем строкам, где они
и стояли, сама таблица не трогается. Совпадающие значения сохраняют взаимный
порядок, пустые уходят в конец — один и тот же вопрос дважды даёт один ответ.
`desc` разворачивает порядок.

Без `order_by` эти четыре читают кадр как есть, то есть в том порядке, в каком
файл случайно записан. Остальные восемь `order_by` отвергают, а не игнорируют:
сумма не зависит от порядка слагаемых, а ранг упорядочивает по значению,
которое читает.

Для доли внутри группы берите `window` с `over`, для доли от всей таблицы —
`compute` с `amount / sum(amount)`.

## Как читать ответы

Строки приходят массивами, соответствующими списку `columns`:

```json
{
  "columns": [{"name": "region", "type": "string"},
              {"name": "amount:sum", "type": "float"}],
  "rows": [["North", 563001.5], ["South", 480000.5]],
  "row_count": 2, "returned": 2, "truncated": false
}
```

- **Проценты приходят долями.** `0.42` это 42%.
- **Валюта и дробные — сырые числа**, а не отформатированные строки:
  форматирование нужно человеку, читающему файл, а не модели, которая считает.
- **`truncated` важен.** Когда он `true`, вы видите часть ответа.

## Как получить файл

`output.path` записывает результат вместо возврата строк:

```json
{"output": {"path": "/data/report.xlsx"}}
```

Расширение выбирает формат — `.xlsx`, `.csv`, `.tsv`, `.parquet`, `.json`,
`.jsonl`, `.yaml`, `.toml`, `.sqlite`. В отличие от JSON выше, этот файл **как
раз** отформатирован для человека: символы валюты, фиксированные знаки после
запятой.

Годится для всего, что пользователь хочет сохранить, и для результатов, слишком
больших, чтобы их возвращать.

## Обо что спотыкаются

**Пути разрешает сервер, а не модель.** Относительный путь считается от того
каталога, где клиент запустил процесс, а это редко там, где данные. Давайте
абсолютные пути.

**Многотабличным файлам нужен `container`.** Для `.xlsx`, `.sqlite` и `.duckdb`
`tuitab_inspect` без него перечислит листы или таблицы; передайте нужную, чтобы
увидеть её колонки.

**У вложенности есть предел.** `tuitab_query` сплющивает JSON, YAML и TOML в
таблицу. Когда структура глубже, чем это переживает, `tuitab_jq` принимает
jq-программу.

**Случайные результаты сообщают своё семя.** `sample` или `dedup` без `seed`
возвращают то, которое выпало, — передав его обратно, вы получите тот же ответ.

## Чего он не сделает

Здесь нет ни SQL, ни произвольного кода. Модель отправляет структурированные
операции, каждая из которых ложится на функцию, уже существовавшую в tuitab, и
получает числа, посчитанные Polars. Это осознанное ограничение, а не
недоделанность: операция, проверенная по схеме, падает громко, когда она неверна,
а строка SQL с опечаткой тихо возвращает неверное число.

Не поддерживаются: подзапросы, self-join и SQL в любом виде.
